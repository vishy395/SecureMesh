# Attack demonstrations

Run only against your own loopback SecureMesh with disposable registrations. No test injection endpoint exists. The actor publishes through MQTTTransport; normal server/device handlers validate every attack. Read-only API snapshots and the existing device SQLite deduplication records supply evidence. The normal operator command/revocation API is used for setup and authorization demonstrations.

## Preconditions and operation

Provision three ACTIVE identities and the server using README installation commands; start authenticated loopback Mosquitto, MQTT-enabled FastAPI and all three simulators. Use the same runtime paths and credentials for the actor. `python -m securemesh.attacks.main --list` lists scenarios. Each invocation emits JSON evidence and exits nonzero with INCONCLUSIVE if evidence cannot be established. MQTT publication alone is never a success criterion. Do not run concurrent operator commands, session rotation or another attack suite during evidence collection. Bounded API histories can cause an inconclusive result under heavy traffic; this fails closed.

`all` runs 12 cases: telemetry/command replay, two tampering variants, three impersonation variants, ephemeral substitution, stale telemetry and three revoked-device interactions. It permanently revokes device-02. Repeat the isolated live test for fresh disposable identities without modifying workspace registrations.

The stale case uses an authorized fixture actor with the target identity to create a valid AEAD envelope with an old inner timestamp. It establishes a new production handshake, replacing the target session. This is necessary to isolate freshness from authentication: an outside actor without keys cannot change an encrypted timestamp successfully. For an individual stale run, stop that target simulator first and restart it afterward. In `all`, device-02 is the freshness fixture and is then revoked; device-01/device-03 remain running. MITM uses an authorized identity only to construct the valid pre-mutation transcript. Impersonation reads public certificates only and signs with a newly generated attacker key, never the victim private key. No secrets are printed.

## Cases and evidence

| Case / threat | Steps | Expected control and behavior | Evidence / observed behavior |
| --- | --- | --- | --- |
| Ciphertext tampering | Capture encrypted telemetry, wait for its committed row, flip one ciphertext bit, republish. | AES-GCM tag fails before replay admission; no invalid receive-state update. | BLOCKED, `invalid_authentication_tag`; original remains stored once. Regression checks memory and database counters before/after invalid delivery. |
| Protected-header tampering | Capture accepted telemetry; increment sequence and update public nonce counter consistently; leave ciphertext/tag unchanged. | Changed AAD invalidates tag. This reaches authentication rather than merely the nonce-format guard. | BLOCKED, `invalid_authentication_tag`; committed original remains unique. |
| Telemetry replay | Capture and wait for acceptance; republish byte-identical canonical envelope. | Authenticated sequence is already processed; no duplicate storage. | BLOCKED, `replay_attempt`, original stored once, session counter evidence. Continuous legitimate traffic can advance counters independently. |
| Command replay | Issue CHANGE_THRESHOLD through normal API; capture command; wait for EXECUTED authenticated ACK; republish exact protected envelope. | Durable delivery digest and command ID deduplicate, returning fresh ALREADY_PROCESSED ACK without another effect. | BLOCKED refers to repeated execution, not refusal to ACK. `duplicate_command` persists at server; one processed ID and unchanged local execution-event count. |
| Unknown identity | Claim device-999 with public fixture certificate and attacker signature. | Registry rejects unenrolled identity. | BLOCKED, `unknown_device`, no new session. |
| Wrong signing key | Claim device-01 with its public certificate but sign with independent attacker Ed25519 key. | Certificate-bound proof of possession fails. | BLOCKED, `invalid_signature`, no new session. |
| Certificate/ID mismatch | Claim target ID using device-03 certificate (device-01 when target is device-03). | Signed certificate identity and registered fingerprint do not bind to claimed device. | BLOCKED, `invalid_certificate`, no new session. Production event intentionally does not distinguish certificate failure details. |
| Ephemeral substitution | Construct valid signed hello; replace device X25519 public key; retain signature; publish hello. | Ed25519 signature over hello fails, handshake cannot establish an authenticated session. | BLOCKED, `invalid_signature` plus `handshake_failure`; unchanged authenticated-session set. Invalid finish hash/signature and failed-session telemetry are separately tested. |
| Stale telemetry | Establish controlled authenticated session; encrypt valid telemetry older than max age plus five seconds; publish; then publish fresh reading. | Authenticated timestamp freshness rejects old plaintext without consuming receive counter; fresh reading succeeds. | BLOCKED, `stale_message`, identical before/after rejection count and sequence; fresh sequence accepted. |
| Revoked telemetry | Capture accepted device-02 reading; revoke via normal API; confirm inactive session rows; republish. | Registry revocation rejects even formerly valid envelopes. | BLOCKED, `revoked_device`, invalidated sessions. |
| Revoked authentication | Construct fresh legitimately signed device-02 hello after revocation; publish. | Admission checks revocation before creating a session. | BLOCKED, `revoked_device` plus `handshake_failure`. |
| Revoked command | Request START to revoked device through the existing operator endpoint. | Server authorization rejects before publishing a command. | BLOCKED, HTTP 409 and `revoked_device_command_attempt`. Other active devices increase telemetry counts. |

Each result contains attack type, target, UTC attempt time, expected/observed outcome, sanitized reason, actual persisted security event, wire SHA-256 message identifier, session/sequence and command ID where relevant, and verification evidence. The protocol has no independent telemetry message ID; the digest labels the exact attempted wire object. Backend events contain their existing ID/time/device/session fields; richer correlation remains in the result, without a database schema change. The dashboard reads the same persisted events, never fabricated attack results.

## Limitations

SecureMesh cryptographically binds the ephemeral X25519 keys to the authenticated handshake transcript, preventing unauthenticated key substitution. This demonstration replaces the device hello key; it is not proof against every MITM, compromised endpoint or malicious trusted CA. Existing unit tests also exercise server response signature/transcript binding.

Revocation is authoritative at the server. It prevents new commands and admission of telemetry, ACKs and new handshakes. It does not retract a previously valid command already in transit, instantly distribute revocation to devices, or disconnect MQTT clients. Such a command can execute locally within its original lifetime. Claiming that every old device-side command becomes immediately unexecutable would exceed this implementation's guarantees.

The runner needs broker access to emulate a hostile broker/network publisher. Legitimate fixture key access for stale/MITM construction does not represent an impersonation success. Live API observations are bounded and assume no concurrent administrative changes; precise replay-state isolation is covered by deterministic regression tests. Trusted local SQLite supplies durable single-execution evidence for simulated effects, not physical hardware. No external systems, availability attacks, fuzzing campaign or general penetration-testing tools are used.
